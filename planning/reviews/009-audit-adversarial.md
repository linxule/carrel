# Carrel Adversarial Audit — 009
**Date**: 2026-04-20
**Reviewer**: Codex (fresh-eyes pass, post-008 closure)
**Scope**: Whole-repo meta-audit; 12-month on-call lens

## Verdict
Carrel's one-shot mechanical paths are in decent shape: the Python core has clear router/adapter/filer seams, the subprocess surface is disciplined, and the current Python suite passed 62/62 tests in fallback execution. The problem is the control plane around that core: trust, setup, automation, wiki activation, and environment synchronization are still governed mostly by markdown instructions and social contract rather than code boundaries.

The repo is therefore closer to "deployable for careful facilitators" than "operationally safe for a 12-month on-call commitment." The biggest risks are not algorithmic correctness inside `src/carrel/`; they are policy drift, state drift, and privacy surprises at the seam between skills and code.

Runtime note: `uv run pytest` could not complete in this sandbox because `uv` first hit a cache permission error and then panicked. Fallback `.venv/bin/pytest` collected and passed 62/62 tests, matching the repo's stated test count in `CLAUDE.md:7-20`.

## 1. Architectural Integrity
- The "core library is deterministic, no AI" rule is only half true. It is true in the narrow sense that there are no AI SDK imports in the Python package or dependency list (`pyproject.toml:6-15`), and I found no `openai`, `anthropic`, or similar imports under `src/`. It is false in the operational sense that the core library directly calls AI/cloud services from inside `src/carrel/`: Gemini transcription in `src/carrel/transcribe/adapters/gemini.py:8-29`, Groq transcription in `src/carrel/transcribe/adapters/groq.py:10-26`, and Mineru parsing in `src/carrel/convert/adapters/mineru.py:10-20`. That materially contradicts `CLAUDE.md:24-30,82`.
- The layered architecture is real for conversion/transcription. `src/carrel/cli/paper.py:57-111` and `src/carrel/cli/transcript.py:107-166` normalize input, load the profile, and hand off to a pipeline. The pipelines call routers (`src/carrel/convert/pipeline.py:27-54`, `src/carrel/transcribe/router.py:18-48`), and the filers own destination writes (`src/carrel/convert/filer.py:16-63`, `src/carrel/transcribe/filer.py:22-68`). That boundary is concrete, not aspirational.
- The same layered architecture is aspirational for setup, automation, wiki activation, and dashboard synchronization. `/carrel-setup` explicitly tells Claude to overwrite `.carrel/environment.json` and write a root `CLAUDE.md` directly (`commands/carrel-setup.md:56-58`). `/carrel-automate` tells Claude to directly write the `automation` block, update `CLAUDE.md`, update `_meta/my-environment.md`, generate `_meta/automation-prompt.md`, and create `_meta/pending-*.md` files (`commands/carrel-automate.md:61-111`). The environment-setup skill repeats that direct-edit pattern for `CLAUDE.md`, `_meta/my-environment.md`, and `_meta/cheat_sheet.md` (`skills/environment-setup/SKILL.md:94-110,166-212`). Those are policy-critical writes with no deterministic Python boundary analogous to `carrel setup-state`.
- There is abstraction accumulation in the router signatures. Both routers accept `sensitivity` and `hardware`, but both discard them immediately (`src/carrel/convert/router.py:10-18`, `src/carrel/transcribe/router.py:18-26`). That is not just dead weight; it preserves the appearance of a richer policy boundary than the implementation actually has.
- There is also abstraction accumulation in the models. `ConvertOptions` and `TranscribeOptions` exist in `src/carrel/models.py:71-99`, but the CLI and pipelines do not use them as boundary objects; they pass raw parameters around instead (`src/carrel/cli/paper.py:47-56`, `src/carrel/cli/transcript.py:94-105`, `src/carrel/convert/pipeline.py:27-54`). That is not a bug, but it is a sign the package is accumulating "planned shape" faster than actual usage.
- The template layer has already bifurcated. The code only loads root templates from `templates/` via `src/carrel/vault/templates.py:83-103`, but there is a second template tree under `skills/vault-ops/templates/`. The two `vault-scaffold.json` files are already divergent: the root template includes `_meta/local` and database metadata (`templates/vault-scaffold.json:13-24`), while the skill-local copy does not (`skills/vault-ops/templates/vault-scaffold.json:11-30`). That is a pure maintenance liability: one tree is authoritative in code, the other is authoritative only in human context.

## 2. Security Posture
- Researcher data leaves the machine through a small but important set of routes. Local file bytes are handed to local subprocesses for PDF/doc/audio work: `lit parse` in `src/carrel/convert/adapters/liteparse.py:11-26`, `markitdown` in `src/carrel/convert/adapters/markdownify.py:10-27`, and `coli asr` in `src/carrel/transcribe/adapters/coli.py:10-30`. Web URLs are handed to `defuddle` or `markitdown` for network retrieval in `src/carrel/convert/adapters/defuddle.py:11-25,69-80`. Google Docs export runs through the external `gws` CLI in `src/carrel/google/export.py:103-147`. Cloud OCR/transcription sends bytes or URLs to Mineru/Groq/Gemini in `src/carrel/convert/adapters/mineru.py:10-20`, `src/carrel/transcribe/adapters/groq.py:10-26`, and `src/carrel/transcribe/adapters/gemini.py:8-33`.
- Filesystem writes are widespread but concentrated in predictable folders. Converted papers land under `vault/papers/.../paper.md` (`src/carrel/convert/filer.py:24-31,61-63`), transcripts under `vault/transcripts/...` (`src/carrel/transcribe/filer.py:31-37,66-68`), captured URLs under `vault/inbox/...` (`src/carrel/cli/capture.py:34-35,91-92`), exported Google files under `vault/.carrel/exports/...` (`src/carrel/google/export.py:75-77,122-147`), and scaffold/setup state under `.carrel/` and `_meta/` (`src/carrel/vault/scaffold.py:90-118`). The session-start hook also writes `.carrel/plugin-state.json` on each session start (`hooks/check-environment.js:66-70,212-215`).
- The strongest verified security property is subprocess discipline. Every Python subprocess invocation I found uses `asyncio.create_subprocess_exec` with argument arrays, not `shell=True`: `src/carrel/env/audit.py:42-63`, `src/carrel/convert/adapters/liteparse.py:11-26`, `src/carrel/convert/adapters/markdownify.py:10-27`, `src/carrel/convert/adapters/defuddle.py:11-28,69-83`, `src/carrel/transcribe/adapters/coli.py:10-30`, and `src/carrel/google/export.py:81-100`. I found no `shell=True`, `create_subprocess_shell`, or `os.system` usage in the runtime source.
- The weakest verified security property is sensitivity handling. Both routers accept `sensitivity` but ignore it (`src/carrel/convert/router.py:10-18`, `src/carrel/transcribe/router.py:18-26`). The effective cloud gate is `cloud_consent` alone (`src/carrel/consent.py:6-10`, `src/carrel/convert/router.py:28-31`, `src/carrel/transcribe/router.py:40-47`). That conflicts with the product promise "Sensitivity-aware by default. Local-first. Nothing leaves the machine unless explicitly chosen" (`README.md:56-63`) and with the decision tree, which says `sensitivity` plus `cloud_consent` jointly encode policy (`skills/environment-setup/references/decision-tree.md:37-57`). In practice, if a profile has `cloud_consent=true` and the local binary is missing, high-sensitivity content can still route to Mineru/Groq/Gemini.
- There is no hard write-containment check. `resolve_vault()` accepts any explicit path and does not require a `.carrel/` marker (`src/carrel/cli/__init__.py:16-28`). The filers and scaffold then join subpaths relative to that root without verifying the resolved destination still sits underneath the intended vault (`src/carrel/convert/filer.py:24-31`, `src/carrel/transcribe/filer.py:31-37`, `src/carrel/google/export.py:75-77`, `src/carrel/vault/scaffold.py:54-135`).
- `carrel vault new` is path-traversal prone by simple string concatenation. The `name` argument is used directly as `target_dir / f"{name}.md"` in `src/carrel/cli/vault.py:41-64`, with no slugification or containment check. A researcher typo with `/` or `../` is enough to produce unexpected directories or escape the intended note folder. This is a concrete code path, not a hypothetical policy concern.
- [HYPOTHESIS: unverified] A symlinked vault subdirectory could route writes outside the vault root, because none of the filers perform a final `resolve()` plus ancestor check before writing (`src/carrel/convert/filer.py:61-62`, `src/carrel/transcribe/filer.py:66-67`, `src/carrel/vault/scaffold.py:46-51`).
- Google export creates a hidden retention surface with no cleanup story. Raw exported files are stored in `.carrel/exports/` (`src/carrel/google/export.py:75-77`) before conversion and are never removed in `src/carrel/cli/google.py:38-67`. For Imperial deployment, that means a researcher who thinks they only have markdown copies may also have silent `.docx`/`.pdf` duplicates of sensitive Google Docs.

## 3. Long-Term Maintenance Smells
- The biggest non-version multiple-sources-of-truth problem is profile state. `CLAUDE.md` explicitly says interview preferences flow into `environment.json` and vault `CLAUDE.md` and that both "must stay in sync" (`CLAUDE.md:118-123`). The environment-setup skill extends that sync set to `_meta/my-environment.md` and `_meta/cheat_sheet.md` (`skills/environment-setup/SKILL.md:166-173,199-202`). `/carrel-automate` extends it further to `_meta/automation-prompt.md` (`commands/carrel-automate.md:89-103`). Only one of those artifacts has a deterministic generator: `_meta/cheat_sheet.md` via `src/carrel/vault/templates.py:153-194`. `_meta/my-environment.md` is only scaffolded once in `src/carrel/vault/scaffold.py:109-111`.
- The cheat-sheet stack is already drifting. The reference template claims it is the thing `render_cheat_sheet()` uses (`skills/environment-setup/references/cheatsheet-template.md:1-4`), and it defines a much richer structure (`skills/environment-setup/references/cheatsheet-template.md:17-180`). The actual renderer ignores that file and hardcodes a different shorter document in `src/carrel/vault/templates.py:153-194`. That is knowledge fragmentation in live form.
- Schema knowledge is also fragmented. The interview protocol correctly defines the canonical flat `ResearcherProfile` schema and tells Claude to validate it (`skills/environment-setup/references/interview-protocol.md:78-140`). The scaffold writes the same flat schema (`src/carrel/vault/scaffold.py:90-102`). But the SessionEnd hook still expects the old nested `env.interview.researcher` object and exits if it is absent (`hooks/session-reflect.js:83-93`). That is not just stale documentation; it is stale runtime behavior.
- The environment setup references already contain at least one stale field contract. `skills/environment-setup/references/toolchain-guide.md:35-42` tells Claude to inspect `environment.json.data_types` to decide whether to install audio tooling, but `ResearcherProfile` has no `data_types` field at all (`src/carrel/models.py:172-186`). A new contributor reading references before code will learn the wrong schema.
- The hardest part to onboard a contributor into 12 months from now will be locating authority. For setup/automation/wiki, the authoritative behavior is split across `commands/*.md`, `skills/*.md`, hook scripts, templates, and only a small amount of Python (`commands/carrel-setup.md:21-29,56-58`; `commands/carrel-automate.md:61-111`; `skills/automation/SKILL.md:93-125,305-319`; `skills/knowledge-wiki/SKILL.md:36-47`; `hooks/check-environment.js:242-265`). A contributor who only reads `src/` will miss large parts of the operational contract; a contributor who only reads markdown will miss what the code actually validates.

## 4. Trust Enforcement Gap
- The trust model is stored, narrated, and surfaced, but not enforced in code. `AutomationConfig` stores `trust_level` in `src/carrel/models.py:133-146`. The automation skill defines the four trust behaviors in detail (`skills/automation/SKILL.md:93-104`). But the runtime hook only checks freshness and pending file counts; it never branches on `trust_level` (`hooks/check-environment.js:185-209`). I found no Python write path that checks `trust_level` before mutating vault files.
- The wiki system is explicit about this gap. The knowledge-wiki skill says the same `trust_level` governs wiki behavior (`skills/knowledge-wiki/SKILL.md:36-47`), while `trust-activation.md` states plainly that `wiki_preference` and related fields are "not enforced by code hooks" and must be checked by Claude during session orientation (`skills/knowledge-wiki/references/trust-activation.md:45-50`).
- That means trust is currently a prompt contract, not a runtime guard. The evidence is structural: the skill tables describe what Advisory/Consultative/Delegated/Partnership mean (`skills/automation/SKILL.md:97-104`, `skills/knowledge-wiki/SKILL.md:38-47`), but the code only stores the enum (`src/carrel/models.py:30-35,133-146`).
- Worst-case blast radius from a trust misconfiguration is full-vault mutation by an assistant session that has normal file-write permissions. Partnership explicitly authorizes rename/move/reorganize behavior in prompt text (`skills/automation/SKILL.md:101-104`); consultative writes executable proposals to `_meta/pending-approvals.md` (`skills/automation/SKILL.md:305-319`); wiki activation writes `wiki_enabled`, updates `CLAUDE.md`, and creates wiki structure by direct instruction (`skills/knowledge-wiki/references/trust-activation.md:132-145`). Because those flows are not code-gated, the practical blast radius is "whatever the current assistant instance can write in the vault."
- Inference from the above: yes, trust-gated features can be accidentally activated in a zero-shot session. Wiki activation is a direct-edit recipe (`skills/knowledge-wiki/references/trust-activation.md:132-145`), and `/carrel-automate` is a direct-edit recipe for pending decisions, approvals, and overnight prompts (`commands/carrel-automate.md:61-111`). There is no deterministic barrier comparable to `carrel setup-state` that could reject such writes when the trust level is still advisory.

## 5. Missing Capabilities
- I do not see deployment-grade telemetry or observability. The CLI error boundary is `emit_carrel_error()` printing to stderr and exiting (`src/carrel/cli/__init__.py:31-35`). Adapters raise actionable hints but do not persist structured failure data (`src/carrel/convert/adapters/liteparse.py:30-36`, `src/carrel/convert/adapters/defuddle.py:37-55`, `src/carrel/google/export.py:143-147`). The session-start hook prints ephemeral console nudges (`hooks/check-environment.js:289-358`). For Imperial field support, that means no durable diagnostic trail for failed exports, timeouts, auth churn, or routing decisions.
- I do not see an explicit offline mode. The local-first paths exist, but there is no repo-level "offline/air-gapped" control plane that disables network features or preflights them. Network-dependent paths include defuddle/markitdown URL capture (`src/carrel/convert/adapters/defuddle.py:11-25,69-80`), YouTube captions (`src/carrel/transcribe/adapters/youtube_captions.py:39-57`), Google export (`src/carrel/google/export.py:103-147`), and all cloud OCR/transcription adapters (`src/carrel/convert/adapters/mineru.py:10-20`, `src/carrel/transcribe/adapters/groq.py:10-26`, `src/carrel/transcribe/adapters/gemini.py:8-33`).
- I do not see a vault export/import story across machines. The supported CLI surface in `src/carrel/cli/main.py:14-21` includes `capture`, `google`, `paper`, `setup-state`, `transcript`, `vault`, and `env`; the README command list likewise has no vault backup/import/export command (`README.md:40-54`). That is a real gap for researchers moving between Imperial-managed devices and personal laptops.
- The data-loss recovery story is partial at best. Positive: the filers are conservative by default and refuse overwrite without `--force` (`src/carrel/convert/filer.py:46-57`, `src/carrel/transcribe/filer.py:51-62`), Obsidian's `file-recovery` core plugin is enabled in the scaffolded config (`templates/obsidian-config.json:14-19`), and setup-state has a reset CLI (`src/carrel/cli/setup_state.py:122-143`). Missing: no first-party restore/snapshot flow for assistant-written markdown, no cleanup or archival policy for `.carrel/exports/`, and delegated/partnership undo still relies on session checkpoints per prompt text rather than a deterministic revert mechanism (`skills/automation/SKILL.md:101-104,221-224`).
- Another missing piece for deployment is deterministic maintenance of the researcher-facing dashboard. `_meta/my-environment.md` is presented as a "living dashboard" that Claude keeps updated (`templates/my-environment.md:1-3`, `skills/self-improve/SKILL.md:34-45`), but there is no Python command that regenerates it; the only code path is one-time scaffold write in `src/carrel/vault/scaffold.py:109-111`.

## 6. Unintentional Abstractions
- **Narrative shadow state**: the same facts are expected to live simultaneously in `.carrel/environment.json`, vault `CLAUDE.md`, `_meta/my-environment.md`, `_meta/cheat_sheet.md`, and sometimes `_meta/automation-prompt.md` (`CLAUDE.md:118-123`; `skills/environment-setup/SKILL.md:166-173,199-202`; `commands/carrel-automate.md:89-103`). This is not a rewrite complaint; it is a naming complaint. The repo has accumulated a shadow-control-plane of human-readable mirrors.
- **Markdown control plane**: high-stakes workflows are increasingly "implemented" as prose commands plus trust assumptions rather than Python APIs. Setup state escaped that trap via `carrel setup-state`; automation, wiki activation, collaborator handbooks, reflections, and migration still live primarily in markdown (`commands/carrel-automate.md:61-111`, `commands/carrel-share.md:61-89`, `commands/carrel-reflect.md:15-29`, `commands/carrel-migrate.md:11-43`).
- **Template twins**: root `templates/` and `skills/vault-ops/templates/` are conceptually the same abstraction but operationally different, and only one is code-loaded (`src/carrel/vault/templates.py:83-103`). The drift in `vault-scaffold.json` shows this accumulation has already started to bite (`templates/vault-scaffold.json:13-24` vs `skills/vault-ops/templates/vault-scaffold.json:11-30`).
- **Parametric ghosts**: `sensitivity`, `hardware`, `ConvertOptions`, and `TranscribeOptions` still advertise a richer policy layer than the runtime uses (`src/carrel/models.py:71-99`; `src/carrel/convert/router.py:10-18`; `src/carrel/transcribe/router.py:18-26`). That is the kind of abstraction that future contributors assume is load-bearing and later discover is inert.

## 7. Three Predicted Bug Classes
- **Bug class 1: Flat-profile hooks silently no-op.** Canonical setup now writes flat `ResearcherProfile` JSON (`skills/environment-setup/references/interview-protocol.md:78-140`; `src/carrel/vault/scaffold.py:90-102`), but the SessionEnd hook only looks for `env.interview?.researcher` and exits if it is missing (`hooks/session-reflect.js:83-93`). First-month pilot symptom: researchers report that end-of-session reflection prompts never appear, so friction/feedback loops quietly die.
- **Bug class 2: Privacy-routing surprises when a profile drifts toward cloud consent.** `paper convert` and `transcript create` pass `sensitivity` through the stack (`src/carrel/cli/paper.py:82-85`; `src/carrel/cli/transcript.py:63-72,133-147`), but both routers ignore it (`src/carrel/convert/router.py:18-31`; `src/carrel/transcribe/router.py:26-47`). First-month pilot symptom: a researcher who earlier allowed cloud tools for one workflow later finds a missing local binary pushes a sensitive PDF/audio file into Mineru/Groq/Gemini because `cloud_consent` became the only live gate.
- **Bug class 3: Post-setup state drift makes Claude and the dashboard disagree.** The skills tell Claude to keep `environment.json`, `CLAUDE.md`, `_meta/my-environment.md`, and `_meta/cheat_sheet.md` synchronized (`skills/environment-setup/SKILL.md:166-173,199-202`; `commands/carrel-automate.md:61-103`), but only `_meta/cheat_sheet.md` has a deterministic generator (`src/carrel/vault/templates.py:153-194`) and `_meta/my-environment.md` is only scaffolded once (`src/carrel/vault/scaffold.py:109-111`). First-month pilot symptom: after a researcher adds a key, changes sensitivity, or enables automation/wiki, one surface says the tool is active, another says it is deferred, and Claude behaves according to whichever document it happened to read first.

## Top Refusal List
- I would refuse ownership of delegated/partnership automation incidents until trust has a code boundary, not just a markdown table. Today the trust semantics live in `skills/automation/SKILL.md:97-104`, but the runtime only stores the enum in `src/carrel/models.py:133-146` and never enforces it.
- I would refuse ownership of privacy routing until sensitivity is made mechanically meaningful. The product promise is local-first for sensitive work (`README.md:56-63`; `skills/environment-setup/references/decision-tree.md:37-57`), but the live routers ignore `sensitivity` (`src/carrel/convert/router.py:18-31`; `src/carrel/transcribe/router.py:26-47`).
- I would refuse ownership of long-horizon support for environment/profile drift until there is one deterministic sync surface for researcher state. Right now the repo asks Claude to hand-maintain multiple mirrors of the same truth (`CLAUDE.md:118-123`; `skills/environment-setup/SKILL.md:199-202`; `commands/carrel-automate.md:89-103`), and only one of those mirrors has a real generator (`src/carrel/vault/templates.py:153-194`).
